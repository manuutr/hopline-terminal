# What Hopline is for

A network engineer working an incident often has a terminal on each side of a fault, a ticket, and a model in another window. By the time a routing table makes it into the model, its device, VRF and collection command may have been lost. Its customer labels may still be there.

Hopline keeps a command attached to the session that produced it. Parsers turn suitable output into rows. An engineer can investigate alone, attach evidence to a question, or choose several devices for a read-only fleet investigation. Each worker can point to the device output behind its conclusion.

The model brings language and reasoning. The harness supplies tools with a defined scope, masks recognized private labels before a provider request, checks commands, and asks the engineer to review changes. Choosing an on-device model keeps inference local. The terminal and parsers work on their own.

An example starts with a healthy IPsec tunnel and an application timeout. The decisive observation is which routing table handles the **return** packet.
